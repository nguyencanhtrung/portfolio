# Architecture changes

## Publish the grouped project catalog

- Problem: The production Projects page rendered one undifferentiated list and temporarily mounted a development-only prototype with query-string controls. The approved C direction needed two durable categories without making the prototype part of production.
- Design decision: `src/data/projectCatalog.ts` owns locale-specific catalog content and explicit entry contracts. `ProjectCatalogCategory`, `ProjectCatalogEntry`, and `ProjectCatalogIcon` own rendering and receive typed props. Professional entries reuse the existing project facts and routes; independent projects are per-locale arrays so adding another project is a data change. The category rail, icon-first headings, responsive entry directions, and theme-aware SVG art stay within the existing Datasheet Memoir template. The ASR Studio source is described as publicly available under PolyForm Noncommercial and links to GitHub, setup, and its website.
- Trade-offs and rejected options: The dev prototype was not promoted as a component or left behind as a hidden production branch. A shared category/entry renderer was chosen over separate hand-written sections so content growth does not add view branches. The approved category rail is retained even though a single-column list would be shorter to implement; the rail makes the two kinds of work scannable without adding jump navigation.
- Verification evidence: `/tmp/portfolio-production-run/catalog-build.log` records the normal Astro production build and Pagefind run. `/tmp/portfolio-production-run/catalog-check.log` records EN/VI catalog assertions, role labels, ASR links/logo path, prototype-control absence, and `git diff --check`.
- Prototype archive: Approved snapshots and the throwaway prototype are preserved on `prototype/projects-c-approved` at commit `6cd4439544b87db8ed24ea88979a2c3a6719dbee`; the main branch does not include the preview middleware or prototype files.
- Follow-ups: Add future independent projects to both locale arrays in `src/data/projectCatalog.ts`, including a stable `id`, localized copy, and links.
- Tag: architecture, design. Target document: this file.

## Archive Blog routes without deleting content

- Problem: Blog index, pagination, post routes, and RSS were public even though this release closes the Blog surface. The About copy also promised a visible blog, and Pagefind could index the rendered posts.
- Design decision: Move the seven route source modules from `src/pages/blog`, `src/pages/vi/blog`, and `src/pages/rss.xml.js` to the matching `src/archived-pages` paths. Astro therefore stops generating those routes while the content collection, Blog components, and image files remain available for restoration. Remove Blog/RSS links and feed metadata from the shared shell and remove the About claim.
- Trade-offs and rejected options: Content was not deleted, and the route modules were not commented out or hidden with middleware; relocation keeps restoration explicit and reversible. Blog components and translation strings remain because they are the preserved implementation boundary, not public discovery.
- Verification evidence: `/tmp/portfolio-production-run/blog-closure-build.log` records the normal Astro build generating only the remaining public routes and Pagefind output. `/tmp/portfolio-production-run/blog-closure-check.log` records absence of Blog/RSS paths and references in `dist`, preservation of the 71 content files and Blog components, and `git diff --check`.
- Restoration: Move the modules back from `src/archived-pages` to their original `src/pages` paths, restore the shell nav/feed links and About copy, then run the normal build and verify the generated routes before publishing.
- Follow-ups: Keep archived route modules out of the production route tree until the Blog surface is explicitly reopened.
- Tag: architecture, content lifecycle. Target document: this file.

## Separate the shared shell and theme ownership

- Problem: `Base.astro` owned metadata, header/footer markup, navigation, theme initialization, theme persistence, and the Mermaid event boundary in one file. Theme reads and writes were unguarded, so blocked storage could break page initialization or toggling.
- Design decision: `Base.astro` now owns fonts, global styles, document metadata, locale alternates, and the page slot. `SiteHeader.astro` and `SiteFooter.astro` own their typed props, markup, and visual behavior. `src/lib/theme.ts` owns pure theme validation, system fallback, toggling, and guarded storage helpers; `src/scripts/theme.ts` is the only DOM/storage effect boundary and continues to dispatch `themechange` for Mermaid. This follows the Learn frontend principle of keeping state ownership close to the parts that need it, passing explicit props, and avoiding a reducer/store for static catalog state.
- Trade-offs and rejected options: Theme state was not moved into a framework store or reducer because the only persistent value is the document theme preference. The same theme entry is bundled into a synchronous head initializer rather than duplicating policy in each page; event binding waits for the body to be parsed. Header/footer extraction adds two components, but gives the shell clear boundaries and keeps Base focused on document concerns.
- Verification evidence: `/tmp/portfolio-production-run/theme-tests.log` records 4 passing pure theme/storage tests. `/tmp/portfolio-production-run/final-build.log` records the final normal Astro build generating 15 public pages and Pagefind output over 15 pages in both languages. `/tmp/portfolio-production-run/architecture-check.log` records ownership and source/output assertions. `/tmp/portfolio-production-run/browser-smoke.log` records EN/VI catalog rendering, 2 category groups, 4 professional entries, theme persistence after reload, mobile one-column layout, and no horizontal overflow on normal Astro preview port 4323.
- Follow-ups: Keep future interactive state at its nearest owner; add a shared state coordinator only if a real cross-component workflow requires it.
- Tag: architecture, interaction-state. Target document: this file.


## Apply the shared theme before first paint

- Problem: Moving initialization from the synchronous document head to a deferred module allowed the light default to paint before a saved or system dark preference was applied on slow loads.
- Design decision: A small build plugin bundles the existing typed theme entry and its pure helpers into an inline head script. It applies the theme during head parsing, and binds the toggle after the DOM is ready. Policy, guarded storage access and event wiring remain in their existing modules; no second initializer or additional theme state is introduced. The plugin watches both source modules during development.
- Trade-offs: The bootstrap is included in each document instead of fetched as a separate module, preventing a theme flash even when module requests are delayed. esbuild, already present in the lockfile through the existing toolchain, is declared directly as a build dependency. A handwritten duplicate head policy was rejected to avoid drift.
- Verification evidence: `/tmp/portfolio-production-run/theme-bootstrap-tests.log` records tests of the bundled entry before any body content exists, including saved/system dark and blocked storage. `/tmp/portfolio-production-run/theme-bootstrap-build.log` records the production build. Independent browser verification and a fresh review cover the replacement candidate before handoff.
- Follow-ups: Keep changes to theme policy in the existing theme modules; the head bootstrap is generated from those sources.
- Tag: architecture, interaction-state. Target document: this file.

## Add the approved soft carrier-wave section break

- Problem: The mobile carrier ornament was visually associated with the final Robotics illustration, while the independent-project links were separated from the project logo. The approved prototype makes the wave itself the category boundary and groups project actions below logo metadata.
- Design decision: `ProjectSectionBreak.astro` renders a static SVG fallback and localized pause control. `src/lib/section-wave.ts` supplies the same path calculation to server rendering and the browser. `src/scripts/section-wave.ts` owns each divider's phase and pause preference; intersection, page visibility and reduced-motion preference determine whether it schedules frames. Category/entry props describe which entry closes at a break. Mobile removes that entry's closing border and centers the full-width wave on the boundary, with space before the next category. Shared theme tokens and the approved faint strokes are retained. Independent entries now render only Github and Website below the logo metadata in both locales.
- Trade-offs: SVG path updates stay confined to the separator and stop outside the visible page. A static divider remains with scripts disabled or reduced motion enabled; the pause control is progressively revealed. No animation dependency or global application store is added. The earlier miniature beside the mobile category icon was rejected during prototype review.
- Verification evidence: `/tmp/portfolio-wave-build.log` records the production build; `/tmp/portfolio-wave-unit.log` records the existing unit tests. `/tmp/portfolio-wave-browser.json` records desktop/mobile and locale/theme cases, exact mobile boundary alignment, faint stroke opacity, action placement and animation lifecycle checks; `/tmp/check-production-wave.mjs` is the external browser harness. Screenshot artifacts use `/tmp/production-wave-` prefixes.
- Prototype archive: `prototype/projects-wave-approved` at `8fe3d50185ef1a027d7800bc6c57d6dcee9f0276` preserves the throwaway source and alternatives separately from main. Approved decision: animated B, faint strokes, full-width mobile rule replacement and links under logo; no prototype proxy, query switcher or alternative artwork ships.
- Follow-ups: Keep future animation state local to its divider and preserve static/no-script rendering.
- Tag: architecture, design, accessibility. Target document: this file.
